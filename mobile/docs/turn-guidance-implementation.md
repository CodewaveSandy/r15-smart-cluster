## Ownership and integration

- `MapsNotificationListener` is OS-bound with `BIND_NOTIFICATION_LISTENER_SERVICE`, exported=false and all notification filter types including ongoing/silent. It waits for listener connection before baseline reads. The package `com.google.android.apps.maps` and same user/profile are checked **before extras**; group summaries and ordinary non-ongoing/non-navigation alerts are excluded. The service never creates a GATT or starts a foreground service/connection from a notification.
- `MapsNotifications` holds at most8 bounded Maps candidates,16 opaque ordering hints and one selected observation/core in memory. Listener instance identity fences obsolete callbacks. Older per-key OS post ordering hints can be ignored but wall-clock notification timestamps never establish source age. Baseline reads, identical reposts, replacement keys, polling and optional ETA/summary updates preserve meaningful content age. Listener reconnect/process baseline starts with unknown age. One last action core/time prevents unchanged remove/repost/recovery from making an old turn fresh. Stop clears private state; no notification history is written or logged.
- `MapsNotificationParser` is the bounded English public-extras profile. It accepts anchored explicit turn/keep/straight/continue/U-turn/roundabout phrases, explicit exit numbers and exact arrival/reroute/GPS-loss/pause states. It never treats a place name containing “left” as a left turn. Distances require declared metric/imperial units; decimal dot is supported, positive conversions round up to whole metres and zero stays zero. Exact duplicate candidate cores coalesce; distinct eligible candidates stay ambiguous. Multiple distinct instructions/“then” phrases are neutral; ambiguous distances are omitted. Remaining values/ETA are optional, parsed only when explicitly labelled. Printable ASCII is firmware profile1; unsupported text is reported, never silently transliterated. Overlength wire text is explicitly truncated and neutral. Unknown maneuver/distance/time stays unknown.
- `TurnGuidanceWire` implements exactly R15F/R15U/R15W, little-endian fields, CRC32, sentinels, padding, glyph/range/version checks, global command sequence and separate source revision. No old map UUID is reused.
- `TurnGuidanceSync` runs inside the single `BleBond` ATT scheduler, below existing metadata/telemetry priority. It discovers c01c/c01d/c01e, requests247 and checks actual MTU≥227, reads real readiness, subscribes with read fallback, adopts current matching status/context, opens a fresh stream and completes the monotonic TimeRequest/Confirm exchange. Snapshot rate≤2/s, Presence≤1/2s; source changes coalesce behind one ACK barrier. ATT success is only admission. Matching display sequence/revision/publication is required before the UI says accepted. Timing status reads use a short bounded cadence to fit the firmware500 ms RTT limit;25 s refresh is scheduled conservatively at24 s.
- Missing display ACK triggers a status read and at most2 byte-identical retries. Bad timing is bounded to3 fresh exchanges, then an explicit Retry sharing is needed. Optional incompatibility/read failure does not erase bonds or disable metadata/telemetry. A missing **ATT callback** still uses the existing owner's safe close/reconnect path; it never starts a second operation while one is outstanding. Service Changed invalidates characteristic identities and preserves command ordering on the same secure connection. Reconnect/new tokens invalidate wire timing/ACK state, not source timestamps.
- `ClusterSyncService` owns explicit guidance intent alongside its existing connected-device foreground lifetime. Enable requires a visible user action, active cluster sync, consent, OS access and a connected listener. Screen lock/Flutter disposal does not send Stop. Notification removal immediately queues priority Clear (instead of waiting behind a rate-limited Presence), with750 ms local replacement grace; a replacement reopens a fresh stream without rejuvenating unchanged content. New Stop/revoke reasons can preempt an older pending Clear. Reroute/unsupported/GPS loss first withdraw an old directional snapshot. Stop guidance leaves BLE and Google Maps running. Stop sync/Forget use the existing disconnect path, which also invalidates remote guidance; firmware's independent expiry remains the fallback.
- Permission loss/listener disconnect withdraws guidance and requires explicit Enable after recovery. Listener rebind is documented/bounded (at most3 requests,≥10 s apart per listener generation); no repeated prompts or hidden bond repair. `START_NOT_STICKY`, no boot receiver, no permanent wake lock, no location foreground service, no own GPS and no saved live ride. Only the notification-access explanation/consent is persisted; enabling after process/service recreation is explicit. Existing legacy navigation storage cleanup remains untouched.
- Flutter adds a compact My bike guidance card, consent/settings controls, Enable/Stop/Open Maps/Retry, truthful source/cluster/age state and an expandable private current-standard-fields view. It owns no background polling/GATT/parser. Phone/radar/connection artwork, case-sensitive discovery prefix, numeric approval, My bike telemetry and ordinary navigation remain. Native source/transport DTOs are independent of the Mac preview path; the card is absent there.

Android documents the [listener lifecycle, manifest and filter configuration](https://developer.android.com/reference/android/service/notification/NotificationListenerService). [Public notification extras](https://developer.android.com/reference/android/app/Notification) do **not** guarantee Google Maps' fields, schema, language or cadence. The UI shows private standard fields, parser profile, Maps version and Android API so actual compatibility can be established on the target phone. Nothing is exported automatically. [Notification access settings](https://developer.android.com/reference/android/provider/Settings#ACTION_NOTIFICATION_LISTENER_SETTINGS) grant listener access; normal notification permission is separate.

## First end-to-end device check

1. Flash **both** boards with the matched firmware (`50f6bc2` or later compatible source). First verify the stable vehicle/display connection, phone pairing/numeric approval, name/battery/time and available input telemetry. Guidance needs a fresh two-way UART path.
2. Push the Android changes and let **Mobile APK** compile/package. From the repository root, install the cloud artifact with `bash scripts/install-mobile-apk.sh`. No local SDK/build is needed.
3. Open the companion, connect through the existing connection page, then return to My bike. In Google Maps guidance, tap **Review notification access**, read the explanation and enable **R15 Google Maps guidance** in Android settings. Return; listener status must actually become connected. If needed, use Reconnect listener, wait, then retry. On some sideloaded devices Android may show its own restricted-settings protection; use the device's explicit app-settings control if Android requires it. The app does not bypass OS protections; see [Android restricted settings](https://support.google.com/android/answer/12623953).
4. Tap **Enable guidance before starting the route**. Then Open Google Maps, select the destination/mode there and start navigation. Use English notification instructions for this first profile. Compare Maps notification → companion normalized preview → cluster card. No API key/map-sharing/download step exists.
5. Check one explicit left/right turn and next distance, then keep/U-turn/roundabout/arrival where exposed. Missing fields must be dashes/neutral, not guessed. The app reports accepted only after display ACK; Settings or a warning may hide an otherwise accepted card.
6. If the notification existed before Enable/rebind, source age starts **unknown**, and the display is neutral until an actual meaningful instruction/distance/road change. Identical polls, ETA changes and retries must not refresh it. After30 s unchanged it becomes Last Maps update; after120 s it is update pending. Those firmware limits need validation on long straights.
7. Stop guidance: cluster returns trip/info; BLE name/battery/time/telemetry and Maps navigation continue. Enable again deliberately. End Maps navigation/remove its selected notification: old direction clears immediately, with no delayed packet reviving it. Revoke access/disconnect listener and verify truthful state plus clearing.
8. Lock the phone and leave the app UI: confirm updates still arrive. Check out-of-range/reconnect, Bluetooth off/on, Stop sync, Forget, one-board reset, Activity recreation, process death/force-stop/reboot. A restarted process must not resurrect a saved ride or a falsely fresh baseline. Opening Settings/warnings and2 s display lifecycle must retain precedence.

If it says unsupported/no fields: expand **Current notification fields** on the phone and compare against the actual ongoing Google Maps notification. The first parser may need an explicit profile adjustment for that Maps version. Do not add guessed icons, Accessibility/OCR, hidden extras, a private route API or a map SDK as a silent fallback. If timing fails, retain the actual link/MTU/ACK diagnostics and check both boards' new firmware plus the return UART. Retry sharing does not reset bonds or stop basic sync.
