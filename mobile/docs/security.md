# Security, privacy and permissions

The phone can contain sensitive location, caller, message and media data. Minimize collection: notifications opt-in, previews separately opt-in, no message history or private-content diagnostics. Keep only bounded transient content required for presentation. Clear session content on disconnect/forget; define TTL and cancellation before implementation. No analytics or cloud account is required by this scaffold.

BLE bonding alone is not sufficient authorization for every application operation. Review authenticated device enrollment, physical verification, scoped session capabilities and binding the Wi-Fi peer to the BLE-established identity. Choose maintained cryptographic libraries/protocols; do not invent crypto or equate CRC with trust. Development networking must meet explicit authentication and expiry requirements before being enabled.

Keys belong in OS-protected storage on phone and reviewed vehicle-side protected storage. Display preferences never hold phone credentials. No API secrets, signing files, tokens, private messages, real routes or device identifiers in source control/CI logs. Provider keys need platform restrictions and documented quota limits; mobile bundles cannot keep embedded secrets confidential.

Permissions are least-privilege. Per user instruction (2026-10-30), Android startup checks required BLE access before entering the main screen, rechecks on foreground resume, and requests missing access on launch when Android permits a prompt. Android 12+ requests Nearby devices (BLUETOOTH_SCAN/CONNECT); earlier supported Android versions require fine Location permission and enabled Location services for BLE scans. GPS navigation, notifications, media and background permissions are deferred until implemented/used. Permanent denial leads to app Settings rather than a prompt loop; disabled Bluetooth uses Android's enable dialog. Saved preview reconnect waits for successful access verification; blocked access pauses local heartbeat/retry work without deleting trust or claiming remote disconnection. A cached grant is never authority. Native iOS access/scanning remains unimplemented.

Android behavior follows [Bluetooth permissions](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) and the [BLE scanner API](https://developer.android.com/reference/android/bluetooth/le/BluetoothLeScanner). `neverForLocation` remains appropriate because BLE results are not used to infer location; Android may filter some beacon types under this declaration. Revocation while running changes feature capability; security exceptions must not crash the app. Android notification listener/media/background and location behavior requires real-device tests. Future iOS capability differences are represented explicitly. No inaccessible call controls or arbitrary message access is promised.

Discovery names, addresses and advertised UUIDs are locators/capability hints, not authenticated identities. A device called R15 Cluster is a candidate only. The broad BLE scan never treats a name as pairing authorization or reports an application session from mere discovery/bonding.

Before release: review enrollment/revocation, session replay, malformed/flood input, secrets at rest, transport encryption, dependency licenses, privacy disclosures, backup exclusions and signed build ownership. Release signing and store distribution remain pending; generated debug signing is never production signing. No automatic vehicle command forwarding exists.

The implemented [development bridge](mac-preview-connection.md) uses a stable Keychain-protected development CA/identity and launcher-distributed bearer bootstrap, BLE public endpoint discovery and cluster-approved enrollment. Android persists the session with Keystore-backed AES-GCM and no-backup atomic storage. No secrets are exposed over BLE. This is restricted to developer previews; production enrollment and protected persistent credentials remain unimplemented.

Physical ESP32 milestone: the pre-bond name write is untrusted display metadata only. OS numeric comparison stays explicit. Native GATT plus OS bond observations mean a Bluetooth link, without an encryption/application authorization claim. Only the selected bounded locator/name hint is persisted separately from OS keys. Forget app selection removes neither Android nor cluster bond; its UI explains both-side cleanup. No remote Forget/application control contract was invented.

Connected metadata uses c012 only after Android reports bonding and a sufficient MTU is confirmed. Firmware acceptance of its authenticated write is represented separately from the public c011 enrollment label and live-GATT state. Retry does not create another bond or enrollment request, and refusal never clears trust. The full snapshot stays transient; logs contain numeric MTU/GATT results only, with no labels, codes, keys or payload bytes. Metadata expiry/cancellation and older-firmware fallback do not grant other feature capabilities. See [metadata handoff](phone-connected-metadata-handoff.md).
