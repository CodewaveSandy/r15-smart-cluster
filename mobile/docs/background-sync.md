# Android background-sync strategy and work plan

Updated: 2026-11-01. Status: firmware handoff implemented/build-verified; Android work and physical B1/B2 acceptance pending. Start here for mobile implementation independently of firmware work. Read mobile/AGENTS.md, [architecture](architecture.md#companion-architecture-status-and-approved-ui), [current protocol](protocol.md) and [development](development.md). Firmware work starts at [the firmware plan](../../docs/background-sync.md). The shared first acceptance gate is B1 in that plan.

## Outcome and current gap

The rider connects while the app is visible, later starts a route, locks the screen and pockets the phone. Active device sync and eventually location/navigation must continue independently of Flutter pages. Explicit Disconnect/Stop must still win.

Current app has real pairing, one GATT owner, saved-peer foreground reconnect and authenticated name/battery/UTC updates. `BleBond` takes an Activity; `MainActivity.onDestroy` disposes it. `BleConnection` cancels background retry scheduling and backgrounded saved-connect attempts. Native Handler metadata refreshes every 30 seconds while alive, but no foreground service or process recovery owner exists. The updated vehicle firmware now provides authenticated capabilities, real discrete-input telemetry notifications and diagnostic reads; this app still needs to consume them. Modern GPS permissions and maps remain absent. Current device success is not locked-screen acceptance.

Vehicle firmware now implements c013 capabilities, c014 real discrete-input read/notify snapshots and c015 health reads; [Protocol](protocol.md#background-sync-capabilities-and-telemetry-c013c015) is authoritative for every byte. Existing enrollment/name/battery/time writes and UART frames are preserved. Firmware package/portable static checks and display compatibility build passed on 2026-11-01; [firmware verification](../../docs/background-sync.md#implementation-verification--2026-11-01) records the current image hashes and exact limits. No new BLE hardware/CCCD/MTU or locked-screen acceptance has occurred. Implement M1 and M2 below, then run B1/B2; the firmware developer does not need another UUID-design task before this app work.

The firmware build output is `build/vehicle/sevensemi-s3/firmware.factory.bin`; use the existing guarded user-operated vehicle flashing workflow/actual port. Already-compatible display firmware needs no runtime update for these endpoints. A combined image can overwrite NVS, so allow explicit both-side trust cleanup/re-enrollment after flashing if needed; never assume loss of trust is a background-service bug or weaken pairing to recover. Keep actual flashed hashes with the app acceptance record.

## M1 implement background BLE continuity first

M1 preserves c011/c012 exactly as specified in [protocol](protocol.md). Use the new firmware c013/c014/c015 endpoints below for bidirectional background acceptance; no faster metadata heartbeat, map SDK or GPS permission is required. Firmware implementation is ready to build/flash through existing guards; Android service ownership is still to be implemented.

### Connection ownership

Create a concrete Android started foreground service for the active companion connection, using application/service context for GATT and metadata observations. Retain one serialized GATT owner; adapt the existing `BleBond` rather than adding a second connection or duplicating its operation queue. Keep discovery, enrollment, MTU and writes ordered through actual callbacks; preserve three-second enrollment timing and the existing bounded security retries.

`MainActivity` becomes a lifecycle-safe command/state bridge. Flutter binds/observes current service state on attach/resume, obtains an immediate full snapshot and sends semantic Connect/Disconnect/Forget-selection intents. Unbinding, navigation, widget disposal or Activity destruction must not disconnect an active user-authorized sync session. Remove the current lifecycle cancellation only after service ownership exists. No stale Activity, engine, EventSink or MethodChannel result may be retained by the service. Preserve explicit cancellation and guard late callbacks with current GATT/session generation.

Separate device-connection intent from future route intent: End ride stops GPS/route transfer; explicit Disconnect/Stop sync closes BLE and cancels recovery. Do not erase trust for either. Forget remains confirmed app-selection cleanup plus instructions for Android/cluster bond removal; no remote Forget or hidden Android API is introduced.

### Android configuration

Declare an unexported service with `android:foregroundServiceType="connectedDevice"`, `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_CONNECTED_DEVICE` for applicable API levels. Keep version-compatible behavior and verify actual min/target SDK from the pinned build. Require current Nearby/Bluetooth access before starting; a saved grant is not authority. Start/promote the service promptly while the app is visible on deliberate Connect or the existing foreground saved-reconnect flow. Do not launch a hidden service unconditionally at boot.

Show an ongoing connection notification with accurate Connecting/Connected/Reconnecting state, a return-to-app action and explicit Disconnect/Stop sync. Configure a notification channel and declare/request Android 13+ `POST_NOTIFICATIONS` with an explanation; permission denial does not itself prohibit starting a foreground service, but changes notification visibility. Foreground service declarations/permissions are platform requirements, not a guarantee against termination. Android supports a `connectedDevice` service for sustained BLE communication. [Android BLE background guidance](https://developer.android.com/develop/connectivity/bluetooth/ble/background), [service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission).

Keep M1 native scheduling alive without requiring a running Flutter UI/isolate. WorkManager is for deferrable work; it is not the owner of continuous ride telemetry. Do not use a permanent CPU wake lock or blanket battery-optimization exemption as the initial design. Measure locked-screen gaps and energy first; any narrowly scoped wake mechanism or Samsung battery-setting guidance requires evidence and truthful limitations.

### Recovery, limits and state

Move retries out of the widget/foreground-only Dart lifecycle into the service. A concrete initial policy to implement and validate: the existing four attempts with 1/2/4/8-second delays, then a 30-second cooldown before another bounded round while an active connection intent, permissions, radio and saved bond remain valid. Only one timer/attempt may exist. Preserve current authentication/remote-termination stop decisions; numeric GATT status alone is not a diagnosis. Explicit Stop/Disconnect, selection change, stale/removed bond and permission loss cancel work. Do not auto-pair a refused peer or open enrollment in the background.

Persist only minimal non-secret connection intent/selected-peer hints needed for defined recovery. A persisted “connected” flag never establishes a link. Document behavior for OS process death, recents swipe, Android Active apps Stop, Settings force-stop and phone reboot separately. Do not promise recovery after force-stop or silently defeat OS/user Stop. If Android recreates an eligible service, rebuild native state from real observations under launch restrictions; otherwise the app must explain the required foreground restart. Background-start exemptions/CompanionDeviceManager presence are a later evaluated option, not an assumed entitlement. [Launch restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [user stopping behavior](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping).

Retain separate observations: saved bond, live GATT, accepted/fresh metadata, service running, reconnecting/stopped. Keep 44-byte snapshots current at dispatch, 30-second normal cadence, event coalescing, minimum 1.1-second spacing and 90-second success expiry. An optional GATT operation timeout currently blocks further optional work until reconnect; preserve non-overlap and define an observable bounded recovery action without issuing competing GATT calls or erasing trust. Older firmware remains connected with metadata unsupported.

## M2 integrate the supplied telemetry firmware

The user authorized the telemetry firmware alongside M1. Its contract is now implemented and frozen for this handoff in [protocol c013–c015](protocol.md#background-sync-capabilities-and-telemetry-c013c015), with portable normative examples in `shared/protocol/phone-telemetry-v1-vectors.txt`. Integrate the decoder/native transport in the same service owner as M1, then complete B1/B2 sequentially on hardware. Do not wait for another firmware UUID design or invent a replacement protocol.

### Ordered Android integration

1. Preserve existing enrollment discovery/name timing, OS code comparison, saved reconnect and one GATT. On bonded connection complete current serialized discovery/security handling; discover new characteristics by full UUID, never fixed handles. Handle `onServiceChanged` by invalidating old characteristic references and scheduling a safe rediscovery in that same operation owner. Do not use hidden `refresh()` APIs or erase trust to force service discovery. Report missing new endpoints as older firmware/unsupported while retaining existing metadata.
2. Negotiate MTU 96 or higher using the successful callback; 67 is the minimum for 64-byte telemetry, 83 for 80-byte health. Existing metadata still requires 47. One MTU operation only; use the actual negotiated value. Do not attempt fragmented Read Blob snapshots. Keep optional health unsupported at MTU 67..82 and both new streams unsupported below 67, without breaking BLE/c012.
3. Read c013 after authenticated security completion. If temporarily refused during the OS bond/encryption race, use bounded 1/2/4-second retries in the operation owner, never another pairing request. Validate exact 20 bytes, magic/version/reserved/max connection/length/interval and feature bits; retain the current boot token. A successful c013 read proves this endpoint accepted the authenticated current peer, not navigation availability.
4. Register c014 notifications locally and write its standard CCCD with `ENABLE_NOTIFICATION_VALUE` (`01 00`), awaiting the real descriptor-write callback. The Kotlin operation state machine must now explicitly serialize reads and descriptor writes alongside existing DISCOVERY/ENROLLMENT/MTU/METADATA. No simultaneous Android GATT procedures; unsolicited notifications are observations, not completion of an unrelated operation.
5. Read c014 for a timed full baseline: record actual local monotonic dispatch/callback times and use the returned sender uptime as specified in [Protocol](protocol.md#bounding-delayed-delivery-with-a-timed-baseline). Initial accepted read RTT is <=500ms; until then do not assert fresh inputs. Refresh the timed baseline every 30 seconds in the same operation queue and account for measured drift/quantization. Apply the same sequence rules to notifications/read results. A notification may arrive before that read completes. Bind callbacks to the current GATT generation; validate all bytes/CRC/fields, boot and connection, unsigned wrap ordering, source age and independent receipt age before publication. Do not overwrite newer data with a late baseline. c014 sequence increments on reads as well as notifications, so gaps are normal. Source sequence may repeat briefly; do not invent new measurements from repeated reads.
6. Keep 30-second/event c012 writes active in the foreground service, coalesced with the existing >=1.1-second spacing. Notifications require no phone ACK; a timed c014 baseline read every 30 seconds maintains delivery-age confidence. During B1/B2, optionally read c015 every 10 seconds in the same operation queue; validate its 80 bytes/CRC/boot/connection and record numeric counter deltas/ages. In normal use omit this diagnostic polling unless needed. Never call notification attempt counters proof of phone delivery; observe actual valid callbacks/receipt time.
7. On reconnect or eligible service recreation discard all prior characteristic/token/sequence/receipt state, rediscover, re-read capabilities, renegotiate MTU and restore CCCD/full snapshot. Clear incoming readings immediately on disconnect/permission loss. A missing valid stream or expired source becomes Stale after 1000ms, even if metadata/GATT remains healthy. CCCD unsubscribe ends notifications but should not break metadata; re-enabling cannot exceed 5 Hz. Preserve the no-duplicate-GATT and bounded callback-timeout policy; if recovery requires reconnect, perform it through the single service owner.

### Domain and presentation integration

Decode 64-byte R15T natively or through a concrete typed adapter, then publish immutable quality/source/unit-bearing `BikeTelemetry` and diagnostics to Dart. Only real Available gear may populate Home gear. Speed, RPM, fuel and bike voltage are Unsupported in this firmware, never zero, neutral, phone battery or GPS substitutes. Left/right/high beam are real configured bench GPIO phase observations; retain phase semantics without adding another blink. Do not add an unsolicited dashboard redesign to display them. Trip/Info counters are boot-scoped observations, not commands/actions to replay after recovery. Bind the current stream/metadata freshness and diagnostic state independently from the service running and saved bond.

Use monotonic local time for expiry: packet source age plus the protocol's conservative timed-baseline transport/callback age and local elapsed time reaches 1000 ms -> stale; any 1000 ms gap with no valid packet also -> stream stale. Invalid/duplicate/backward/old-generation data does not reset freshness. c012 metadata-fresh expires at 90 seconds independently and does not extend input freshness. Display heartbeat freshness is separate and does not make phone telemetry unsupported if vehicle acquisition still works.

### Handoff acceptance B2

Compare exact portable normative examples with the decoder manually; reject corrupt CRC, nonzero padding, unknown version, invalid bool/quality, mismatched boot/token and expired/duplicate/backward frames. Automated suites remain deferred.

Verify current metadata and telemetry run simultaneously for 60 minutes locked with the phone untethered; the cluster still displays correct name/battery/time, actual source input changes reach phone, acquisition/source/host gaps remain observed and no queues/heap/stacks grow without explanation. Independently reset each board and cycle radio/range, verify current capabilities/baselines and no code/bond replacement on valid saved reconnect. Preserve warnings, Settings/non-touch navigation and two-second lifecycle artwork. Record phone/OS, revisions/image hashes, numeric ATT/MTU/CCCD results, maximum valid callback gaps/source ages and health deltas. B1/B2 remain pending until these actual observations exist.

## M3 active navigation and pocket operation

After provider selection and licensed embedded-delivery feasibility, keep GPS/routing/rerouting and route progress in an owner that lives as long as the foreground ride service. If using Dart/provider SDK logic, explicitly design its background engine/isolate lifetime; it cannot depend on a disposed UI engine. Flutter pages show snapshots and issue Start/End/recenter intents. Rendering a phone map while visible is separate from maintaining route computation while locked.

Add the `location` foreground-service type and `FOREGROUND_SERVICE_LOCATION` permission where required, modern `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION`, runtime precise/approximate handling and current Location services checks. Start location service work from visible Start ride with granted permissions, before pocketing. Foreground location service access can continue with the screen off; do not automatically require “Allow all the time” merely for this flow. Evaluate `ACCESS_BACKGROUND_LOCATION` separately if the chosen restart/background-start/provider requirements need it. Degrade GPS/navigation independently from BLE when denied/revoked. [Location permission guidance](https://developer.android.com/develop/sensors-and-location/location/permissions).

Add main-manifest `INTERNET` for real provider/network operations; it currently exists only in debug/profile manifests. Review provider keys, restrictions, attribution, quotas, offline/reroute behavior and permitted embedded data transfer before adding dependencies. Keep audio with phone/headset. iOS needs its own native BLE/location background assessment and device verification; Android configuration is not transferable.

Use BLE for reviewed compact navigation data only within measured limits. Wi-Fi bulk maps remain a coordinated firmware dependency; verify cellular internet routing, authentication, resume/backpressure and route cancellation. Do not assume Wi-Fi avoids the 115200 UART bottleneck or that full moving maps are already feasible. B3 acceptance covers locked-screen GPS quality/expiry, reroute/route generations, data loss/recovery, offline/provider failures, real display navigation and foreground-service energy over a representative ride. Initial bench checks precede any bike observation.

## Handoff and definition of done

Give the firmware developer app revision/APK build, phone/OS, service lifecycle policy, supported protocol revision and B1/B2/B3 results with numeric diagnostics. Never log keys, names/addresses, route history or payloads. Both sides record the same gate result; “app stayed connected” alone is insufficient. M1/M2 can now be implemented independently against the supplied firmware contract; B1/B2 require actual joint acceptance. M3 still depends on provider/data-rights and navigation/map firmware review. No fake telemetry or navigation-ready claim is permitted.
