# Android navigation v2 — implementation and APK handoff

Updated 2026-11-04. The Android source implements NAV-M0–M5 against firmware commit `52bae3e`. This records source integration, not Android compilation or physical acceptance. APKs are built only by the existing Mobile APK GitHub Action. No Android SDK, Gradle build, native compilation, automated suite, small-screen or 2× text check was used locally.

## Installed APK journey

1. Open the app. The first-use map explanation offers Enable or Later independently of Bluetooth. Enable requests foreground coarse/fine location; choose Precise for guidance. On later opens the service starts visible location and warms nearby roads automatically after consent and an existing grant. Home and Navigate remain available without pairing; the approved landing/radar and OS approval remain inside Cluster connection. Already-granted saved-peer reconnect is checked without a compulsory Bluetooth permission wall.
2. Navigate shows actual location, horizontal accuracy, nearby roads and local road-name images. There is no Kolkata camera/current-position default. Drag/pinch to browse; Follow returns to GPS. A poor/approximate fix is a hollow point with uncertainty, never confident guidance. Location and map coverage are independent. Initial no-fix view is an unlocated world view, not a claimed position.
3. In map settings enter your own [Geoapify project key](https://myprojects.geoapify.com/). Maps do not require it. No default key or account is bundled. Blank Save removes the key. Searches start at three characters, debounce 400 ms, return at most five results and bias to a fresh fix. Old query generations cannot replace current results.
4. Select a result with fresh precise GPS (≤50 m accuracy). The native provider requests **motorcycle** routing, displays its geometry, destination, distance/time estimates and instructions. Preview alone does not transmit to the cluster. Route overview fits the phone camera.
5. Start navigation explicitly promotes the service to location foreground ownership and downloads the whole planned ±500 m corridor including endpoints and zoom levels 1 through the selected offline detail (default z14, clamped to actual source maximum). Share route also starts navigation/downloads and sends the current cell plus overview/current detailed route window first. BLE pairing/sync is needed only for sharing. Do not interpret a route preview or 100% byte transfer as display guidance or entire offline readiness.
6. Download progress shows completed/total tiles and bytes; cluster progress separately shows received-prefix bytes, complete objects, transport rate, display coverage/source quality and independent Follow/Browse state. Coarser detail is an explicit choice after a blocked download, with new source identity/session; it is never silently applied. Zooming beyond that detail overscales its roads.
7. Stop sharing retains phone navigation/corridor work. End navigation cancels route jobs/sharing, removes the saved route and clears the display route, including End after an acknowledged Stop sharing. Stop sync disconnects BLE and ends cluster work while phone navigation can continue. Notification End navigation/Stop sharing/Stop sync/Stop all are independent intents. Stop all ends continuous location as well; explicit Follow or reopening resumes visible browsing, never the ended ride. Location permission loss ends active navigation; restoring it does not resume a cancelled ride automatically.

## Ownership and canonical cache bridge

`ClusterSyncService` still owns exactly one `BleBond` and one `PhoneLocation`. `NavigationSession` owns location consumption, preview/active route, projection/rerouting, jobs and explicit intents. The Activity only binds, forwards semantic commands and observes snapshots; no Activity, engine, EventSink or channel Result is retained by navigation workers. GATT remains entirely in BleBond's serialized main-thread operation owner.

`VectorMaps` is the sole HTTP/raw-map owner. It retrieves [OpenFreeMap TileJSON](https://tiles.openfreemap.org/planet), validates its HTTPS template and max zoom, and pins that immutable template in private `source.json`. Raw MVT is decoded once into cached road/waterway geometry. The **same cached raw tiles** supply local GeoJSON for MapLibre and the semantic R15O cell encoder. MapLibre receives only `addGeoJsonSource`/`setGeoJsonSource` data: it never uses a second remote vector source, native cache extraction, HTTP server, cleartext permission or duplicate downloader. Semantic display children derive from cached source parents, including z16+ interests over a z14 provider maximum.

The local style has background, road/waterway lines, accuracy, heading and route layers. The phone uses bundled Inter/system fallback to rasterize up to32 Unicode label images into stable reusable sprite slots; it requests no remote style/glyph/sprite resources. This is deliberately road-focused cartography, not the OpenFreeMap Liberty style. MapLibre positioning, camera, gestures and layers remain pinned at0.27.1. OpenStreetMap/OpenMapTiles/OpenFreeMap attribution is visible on the phone and encoded as attribution profile2 for the firmware; search/routes identify Geoapify.

Raw cells and their full SHA-256 sidecars are finalized atomically; malformed protobuf/geometry and corrupt hashes cannot become cached coverage. Disk cache is256 MiB LRU; current nearby area, current phone viewport and active corridor are protected. One IO worker means at most **one** HTTP request in flight (below the planned maximum of two and provider maximum of four); duplicate content keys reuse disk/memory. A separate bounded, one-outstanding progress worker keeps projection from waiting on HTTP. Viewport/corridor/nearby work yields between tiles; the latest viewport/query/route/job generations supersede obsolete work. In-flight HTTPS has12 s connect/20 s read timeouts and can finish one immutable bounded response after cancellation; obsolete results do not activate a route or advance a cancelled job.

The cached TileJSON is the source snapshot, not an assumption of current OSM freshness. Clearing maps while navigation is ended also clears that metadata, so the next fetch selects a new provider snapshot. Raw files cannot be reused across a source reset. The current visible area can immediately warm again. No GPS history is stored. One route preview, with integrity sidecar, can survive process death; it is never restored as active navigation/sharing or live location. End deletes it. Offline manifest finalization happens only after every selected corridor cell exists; entries reference source/configuration, detail, buffer, keys and byte count. All navigation files and the encrypted API key are in no-backup private storage; app backups are disabled.

## Bounds and truthful readiness

- Provider requests are HTTPS-only, host-allowlisted, with redirects disabled and a unique application User-Agent. No public Nominatim autocomplete, Overpass per-pan request or OSMF bulk-tile use is introduced. [OpenFreeMap limits](https://openfreemap.org/quick_start/) apply: each full corridor is bounded to **3000 tiles and50 MiB across all selected zoom levels**, including already cached bytes. A missing response reserves its2 MiB upper bound before admission. Nearby/view warm jobs have8 MiB ceilings; disk full/network/provider/complexity failures retain usable complete data and show blocked status.
- MVT compressed response≤2 MiB, decompressed≤8 MiB, bounded fields/layers/commands,≤100,000 decoded points/tile; phone viewport≤20,000 road features. Twelve decoded raw tiles form the memory LRU. Source z/x/y is clamped, world x wraps, y does not.
- Display cells are clipped at real intersections and quantized to0..4096 with shared boundaries, split into2..8 point records. The fixed `lod2` semantic profile includes arterial/water below z12, local/arterial/water at z12–14, all five kinds at z15+. Labels are printable ASCII≤23 bytes; phone labels retain Unicode. This declared LOD selection is source identity, not a density-based truncation. Any remaining >512 chunks or >32 KiB rejects the whole cell with an explicit zoom-in message. No incomplete cell is labelled full coverage.
- Route provider geometry≤50,000 points, estimates within protocol bounds, validated steps and one two-waypoint leg. Antimeridian routes are explicitly unsupported by this conversion profile. Overview retains endpoints and maneuver anchors, uses bounded simplification at2..32 m error, and rejects >512 remaining points/anchors. Detailed windows retain maneuver anchors with≤1 m simplification error, overlap by up to~200 m/128 original points, and cover up to~4 km or512 simplified points. Dense windows shorten explicitly at their encoded end; ROUTE_NEED obtains the continuation. Original route stays on the phone; no arbitrary route is cut off and called fully projected.
- [Geoapify routing](https://apidocs.geoapify.com/docs/routing/) uses `mode=motorcycle&details=instruction_details`; named instruction types are explicitly translated into firmware maneuver enums. Local request spacing≥500 ms, a conservative2500-unit daily guard (eight reserved per route) and actual provider quota errors are separate. This app-local budget cannot account for other clients using the same key. Provider account restrictions/quotas remain yours; no paid upgrade is automatic.
- Freshness is source elapsed time<2 s, finite nonmock coordinates/accuracy and actual OS precision. Approximate location can show roads/point but cannot snap, advance turns or reroute. Heading needs speed≥2 m/s and bearing accuracy≤45°; GPS speed never populates bike speed. Future observations are rejected at acquisition so they cannot become live later as time catches up.
- Progress projects onto the route with a prior-progress ambiguity penalty; remaining distance/time are estimates. Off-route requires error>max(45 m,2× accuracy), at least five eligible observations across≥5 s, and≥10 s reroute backoff. Network failure preserves the old route and reports failure, with no offline-routing invention. Arrival is an explicit near-end/proximity observation, not automatic Stop. These are development thresholds requiring walk/bench acceptance.

## V2 transport integration

`NavigationWire` implements exact64-byte c019, R15V/c01a commands, R15Y/c01b responses and R15O objects in [protocol.md](protocol.md#phase-2-navigation-extension--implemented-firmware-contract). CRC32, full-object SHA-256, source digest, all boot/secured-link/session tokens, control sequence, object IDs, actual MTU and validated ranges precede publication. Old firmware reports v2 unavailable while the phone map/navigation works. Existing strict v1 codec is retained, but this UI does not silently switch to Kolkata/v1 or send v2 through c017.

`NavigationSync` uses one ATT procedure at a time through BleBond while retaining up to four downstream-unacknowledged DATA commands. Controls are barriers; metadata/telemetry and latest location/progress outrank bulk. Credit uses current display/bridge free slots and actual MTU payload capacity. Pacing counts exact escaped inner bytes plus conservative bounded UART-fragment overhead under4096 encoded B/s. Only valid display cumulative ACK offsets advance transfer. ATT success alone is admission. ACK timeout reads Status, retries identical unacknowledged packets at most three times, then requests reconnect through the existing owner. No partial cross-connection resume. Complete full-hash HAVE rebinding is attempted before retransmitting each object.

STATUS, INTEREST and ROUTE_NEED each retain their own latest notification slot. Missing interests invalidate corresponding local assumptions and fetch/derive at most four requested cells; phone camera/route do not follow a display drag. Route windows/overview/current cell activate only as matching complete context; not-ready activation refreshes the actual current cell rather than inventing readiness. Timing uses actual dispatch/callback T0/T1,≤500 ms RTT,25 s refresh and30 s expiry. Rejected timing is renewed; expired status, changed service or missing callback clears the old connection owner before recovery. Reconnect uses a fresh capability/session/anchor and full-hash rebinds. Stop/Cancel preempt queued bulk, and route revisions do not attach new progress to old geometry.

Local evidence: Dart formatting and static analysis; all affected Kotlin parsed using the standalone ktfmt0.54 formatter (new modules formatted; existing modules dry-run parsed), without Android compilation; source review against current firmware protocol/store, provider primary documentation and pinned MapLibre APIs. No local APK/Gradle/native compilation, automated tests, Android runtime/visual capture, actual provider-key request, BLE throughput measurement or physical acceptance is claimed. GitHub Actions must compile Kotlin/Android and package the APK. Keep the APK commit/run/hash and both flashed firmware revisions with the results.

bash scripts/install-mobile-apk.sh
